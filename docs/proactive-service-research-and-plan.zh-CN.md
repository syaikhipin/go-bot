# 主动唤醒服务机制：Muse、Grok Bot 与 dots 重新调研

核对日期：2026-11-21。本文只梳理官方披露的行为与机制，不是 Go Bot 的实施定稿，也不代表功能已实现。

本轮重新从产品资料出发。此前讨论过的独立跟进模块、内部 schedule 入口、单一创建入口及每账号主 Agent 等设计，均不作为本轮预设。暂不讨论手机系统推送或安卓后台保活。

## 1. 先区分四件不同的事

| 环节 | 要回答的问题 |
| --- | --- |
| 触发执行 | 用户没有发新消息，为什么会开始一次工作？ |
| 决定工作 | 这次要继续什么、调查什么，使用哪些相关上下文？ |
| 决定呈现 | 结果是否值得现在告诉用户，还是保存后安静结束？ |
| 决定行动权限 | 已经选定的操作是否允许执行、需要审批或交还用户？ |

审批回答最后一个问题，不能由它推出前三个问题的实现。产品所说的“主动”也可能包括自主跟进、主动建议、事件自动化等不同能力，需要逐项核对。

## 2. Muse

### 2.1 官方明确描述的主动行为

用户给出目标或任务后，Muse 会按时间安排及相关事件继续推进；后台工作完成后，判断是否有有意义的新结果或需要用户输入，再决定展示。它采用主聊天并提供侧边聊天，也提供目标与活动查看入口，用户可以调整主动联系的程度。[设计说明，2026-09-08](https://muse.ai/blog/how-we-designed-muse)

公开资料支持的行为顺序是：

```text
目标或任务
  → 时间安排 / 相关事件
  → 后台继续推进
  → 判断结果是否值得展示
  → 必要时在聊天中联系用户
```

这是产品行为归纳，不是官方后台进程调用图。

### 2.2 运行与权限基础

技术文章说明每个用户有专属 Linux VM，运行 Harness、浏览器、文件及并行子 Agent，并支持 cron。客户端连接该 VM。Sentinel 是独立权限判定服务，负责连接器动作及网络出口等权限决定。[技术说明，2026-09-08](https://muse.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)

### 2.3 不能从资料中确定的部分

- 哪些相关事件由 webhook、轮询或其他机制采集。
- 谁提出下次时间：模型、确定性代码，还是两者结合。
- 是否存在统一 heartbeat、其周期、空闲策略及退避算法。
- “值得展示”的模型、规则、阈值和去重状态结构。
- cron、目标跟踪及主动研究是否共用同一任务表和执行入口。

**看到支持 cron，不能进一步断言全部主动性都由模型调用 cron 工具实现。**

## 3. Grok Bot

### 3.1 自主 check-in：发现机会后先提议

官方 initiative 页面明确列出主动提出能接手的工作、提醒应用掉线，以及在 X Chat 跟进对话。主动联系主要由 primary Bot 发起；该页面描述的行为是先提议，用户接受后再执行，风险动作仍需审批。关闭通知不等于停止 check-in。[When Your Bot Takes Initiative，2026-11-11](https://docs.x.ai/grok-bot/initiative)

```text
发现可以帮助的工作 / 连接问题 / 对话跟进机会
  → primary Bot 主动联系
  → 用户接受建议
  → 正常任务执行
```

这里的“先提议”适用于该页面描述的主动建议，不能扩大成“Grok 的全部后台工作都必须先问用户”。

### 3.2 Routine：已经配置好的时间或事件执行

Routine 保存工作指令及触发条件，由拥有它的 Bot 执行。触发可以是时间、支持的服务事件、发给 Bot 的邮件或 webhook；连接某个应用的读取工具与建立事件触发器是不同能力。只处理触发器建立后的新活动；webhook 接收成功不代表任务已完成，结果需要到聊天中查看。[Skills and routines](https://docs.x.ai/grok-bot/skills-routines-and-automations)

```text
保存指令 + 时间 / 事件条件
  → 触发 routine
  → 所属 Bot 执行
  → 结果进入聊天；必要动作按权限处理
```

Routine 可以查看、修改、暂停和测试。这是公开程度较高的自动化机制，但不证明自主 check-in 也采用相同调度链路。

### 3.3 长期身份和上下文

primary Bot 是主要联系及协调者，专门 Bot 可以承担特定工作。官方说明 Bot 有自己的记忆和工作记录，部分用户基础资料跨 Bot 共享。[How Grok Bot works](https://docs.x.ai/grok-bot/how-grok-bot-works)、[Create and manage Bots](https://docs.x.ai/grok-bot/bots)

这意味着公开产品中的 Bot 身份、记忆和 routine 归属不只是一个临时模型请求；不能直接把每个 Bot 等同于我们当前的每个 session。

### 3.4 没有确定的算法细节

本轮核对的官方页面没有说明 check-in 的首次唤醒来源、周期、是否全局扫描、如何排序候选事项、是否调用额外模型，以及如何选择下一次唤醒时间。Routine 的文档不能用于补齐这些未知部分。

## 4. OpenAI dots

### 4.1 已交办工作可以自主暂停与继续

官方文档明确说明，dot 可以在对话之间继续已交办工作，自行决定何时暂停、再次唤醒。用户也可以指定时间或支持的事件；不需要给每一次跟进都设置固定周期。dot 可以分派后台 Agent，用户仍可继续与它对话。[Assigned work](https://learn.chatgpt.com/docs/dots/tasks-and-memory#assigned-work)

```text
用户交办一个持续目标
  → dot 推进、等待或分派工作
  → 自行决定何时继续
  → 带回结果或需要用户判断的问题
```

**“自行决定唤醒”是已披露能力；“通过哪个工具或内部队列兑现决定”没有公开。**

### 4.2 固定时间工作仍有保存的 schedule

官方单独说明 recurring tasks：需要保存检查内容、时间及时区、通知条件和交付位置，可以在 Scheduled 查看和管理。停止当前工作与取消将来的 schedule 是不同动作。[Recurring tasks](https://learn.chatgpt.com/docs/dots/tasks-and-memory#recurring-tasks)

因此，dots 同时存在“固定时间的已保存工作”和“不要求用户为每次跟进设定固定时间的持续工作”。这不足以证明二者底层一定分离，也不足以证明二者一定共享调度器。

### 4.3 事件监控需要建立具体监控条件

支持的连接服务可以触发工作，例如新 bug 报告。用户应说明要关注哪些事件及何时告知；仅连接应用本身不会自动创建事件监控任务。[Event monitoring](https://learn.chatgpt.com/docs/dots/tasks-and-memory#event-monitoring)

这是明确配置的事件监控，与下一项自主研究不同。

### 4.4 主动研究：没有新请求，也能寻找有用关联

后台 Agent 可以在允许读取的信息中研究、保存私有笔记，并关联以前的工作。例如发现新发布决定与以前的草稿冲突。研究结果先回报给 dot，由 dot 提出建议或问题；研究工具本身不能发消息、修改外部应用或控制浏览器、电脑。[Proactive research](https://learn.chatgpt.com/docs/dots/tasks-and-memory#proactive-research)

```text
允许读取的信息 + 相关历史与工作
  → 后台研究并形成发现
  → 回报给 dot
  → dot 决定如何告知或继续
```

**上述资料没有说明“第一次后台研究是谁、何时触发”。** 不能把这条已公开的结果交还关系，写成已公开的 heartbeat 算法。

### 4.5 上下文和权限如何支持持续性

dot 使用当前对话、相关记忆和自己的工作笔记；后台任务接收选定的任务上下文，不自动得到全部历史。可通过过去的对话检索补充信息。[Context and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory#context-and-memory)

行动审核判断是否可执行、需要用户批准或需要交还用户操作；范围明确的持续指令可以覆盖未来的对应动作。[How action review works](https://learn.chatgpt.com/docs/dots/controls#how-action-review-works)

审批机制界定行动范围，但不能据此解释主动研究或自主跟进的触发算法。

## 5. 横向对照

| 问题 | Muse | Grok Bot | dots |
| --- | --- | --- | --- |
| 已交办工作如何继续 | 公开说明按计划和相关事件继续 | 可由拥有该工作的 Bot 及 routine 推进 | 明确说明可自主暂停与再次唤醒 |
| 时间触发 | 已说明 schedule/cron 能力，未公开调度接口 | Routine 有可管理的时间规则 | Recurring tasks 有保存的 schedule |
| 事件触发 | 公开说明响应相关事件，采集细节未披露 | Routine 明确支持服务事件及 webhook | 支持服务事件监控，需明确监控条件 |
| 没有新请求的帮助机会 | 有主动联系及后台工作，独立发现流程未详述 | primary Bot 主动建议、提醒连接问题与跟进 | 单独描述允许信息上的主动研究 |
| 何时联系用户 | 后台结果有新意或需要输入时 | check-in 先提议；routine 交付结果 | 后台研究回报 dot，由 dot 提建议或问题 |
| 对话与持续身份 | 主聊天与侧边聊天 | primary Bot 与专门 Bot | 同一 dot 协调多个工作和后台任务 |
| 下一次唤醒算法 | 未找到公开细节 | check-in 未找到公开细节 | 未找到公开细节，仅披露能自主决定 |

表格是各文档的归纳，不代表三家采用同一种内部实现。

## 6. 对“主动唤醒机制”能够得出的结论

### 6.1 时间、事件和自主发现不能互相替代

保存的时间任务解释“到点运行”；事件监控解释“发生某事后运行”；自主发现解释“用户没有逐项交办时也能找到帮助机会”。三家产品对这些能力的披露程度不同，不能统称为一个 cron 循环。

### 6.2 运行与联系用户是两个决定

Muse 明确描述执行后的结果筛选；Grok 的 check-in 与 routine 有不同的联系行为；dots 的后台研究先回报 dot。执行了一次后台工作，不必等价于立即给用户发一个气泡。

### 6.3 产品里的长期 Agent 身份不等于单条会话

三家都有持续跟踪工作和统一联系用户的产品概念；Grok 与 dots 还明确描述协调其他 Bot 或后台任务。它们的前台聊天、工作执行和长期上下文之间如何对应，不能直接按我们的 session 对象代入。

### 6.4 我们最关心的内部算法仍有证据缺口

本轮资料不能回答：

1. 谁触发首次自主检查，是否有固定周期。
2. 谁选择下一次检查时间，采用何种结构化结果。
3. 如何在没有新消息时选择候选事项与检索上下文。
4. 是否有专用判断模型，以及何时跳过模型调用。
5. 如何合并同时到来的事件与时间任务、识别重复安排。
6. 主动唤醒、普通 schedule、后台研究是否共用任务存储。

因此，此前给出的“模型保存跟进 → 主动模块登记 schedule”或“必须单一创建入口”等链路，应视为我们的候选设计，不能称为三家机制的还原。本轮不以这些候选设计作为事实结论。

## 7. 后续设计应先回答的全局问题

以下是后续 Go Bot 设计的问题清单，不是新的实施方案：

- 长期个人 Agent 的逻辑身份、会话和后台研究如何对应。
- 当前已有 schedule 在主动运行中承担哪些职责，与其他触发如何协调。
- 首次主动研究、用户交办后的继续执行，是否需要不同的运行条件。
- 运行时如何获知已有安排、正在运行的工作及已经交付的发现。
- 哪些决定由模型完成，哪些约束由 Go 确定性执行。
- 如何让模型有机会主动推进，又避免重复工作、空转和频繁打扰。

在这些关系确定之前，不先增加第二套任务记录、改 schedule 工具语义或规定新的调度入口。现有 Go 代码保持不变。
