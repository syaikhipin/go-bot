# 主动服务：现有产品机制调研与 Go Bot 方案

调研日期：2026-11-21。状态：**调研及提案，尚未实现主动服务功能**。

本文先记录别家的实际做法，再给出 Go Bot 的设计建议。闭源产品依据官方披露，不将产品表现推断成未公开的调度实现；开源项目同时核对源代码。

## 1. 主动服务实际上包含哪些环节

不能只增加一个“定时向模型发送消息”的循环。需要分别回答：

1. **为什么再次工作**：用户交办了持续职责、时间到了、外部数据变化、之前的工作结束了，还是系统发现了新的关联？
2. **如何继续工作**：找到原职责、会话、工作目录和最新信息，进入正常 Agent 执行流程。
3. **是否告诉用户**：没有变化可以静默；有重要进展、风险或需要决策时才形成可见消息。
4. **如何到达用户**：会话内消息、在线客户端实时更新、手机系统通知是不同能力。

其中，长期记忆解决“记得什么”，调度解决“什么时候运行”，它们本身都不等于主动服务。

## 2. Muse：围绕目标持续工作，完成后再决定是否通知

官方设计文章明确披露：设定目标或任务之后，Muse 会根据计划及相关事件继续推进；后台工作完成后，再评估结果是否值得展示。只有出现有意义的新信息或需要用户输入，才通知用户。用户也可以要求减少、增加或关闭主动联系。[来源：How We Designed Muse](https://muse.ai/blog/how-we-designed-muse)

官方技术文章进一步说明：Harness、浏览器、命令和文件在用户专属 VM 的运行环境中；该环境支持并发子 Agent 和 cron，客户端连接 VM。连接器提供外部服务能力，动作权限由独立的 Sentinel 判断，而不是因为任务在后台运行就自动获得更高权限。[来源：How We Built Safety Into Muse](https://muse.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)

可确认的流程是：

```text
用户目标 / 相关事件 / 到期计划
  → 在持续存在的运行环境内推进工作
  → 评估结果的新意和重要性
  → 必要时主动联系；后续动作仍受权限约束
```

**未披露**：通用检查周期、事件订阅内部实现、任务队列及通知评分算法。不能宣称 Muse 使用某个固定间隔的 heartbeat，也不能将 Sentinel 的实现直接当成我们现有权限模块的能力。

对 Go Bot 的启示：围绕用户目标安排后续工作；把“后台做完”与“需要发消息”分开。无需复制其专属 VM 内全部安全基础设施。

## 3. Grok Bot：主动跟进与明确的 routine 分开

### 3.1 主动跟进

官方说明主动联系通常由 primary Bot 发起，包括提出可以接手的工作、发现应用掉线、跟进对话。它会先提出建议，用户接受后再执行；敏感动作仍需审批。关闭通知只影响提醒，并不等于关闭后台 check-in。[来源：When Your Bot Takes Initiative](https://docs.x.ai/grok-bot/initiative)

这揭示了两个独立开关：**是否执行主动检查**、**是否提醒用户**。它们不能混成一个“通知”开关。

### 3.2 Routine 的具体触发机制

Routine 保存工作指令及运行条件，在云端执行；条件可以是时间，也可以是 Slack、邮件、GitHub 等事件或 webhook。官方特别区分“连接应用以便调用它”和“配置触发器以启动工作”。Webhook 被接受代表开始一次运行，不代表任务已经成功完成。用户可以查看、暂停、测试或删除 routine。[来源：Skills and routines](https://docs.x.ai/grok-bot/skills-routines-and-automations)

```text
保存指令 + 触发条件
  → 云端接收匹配的新事件 / 到达计划时间
  → 创建运行
  → 正常调用工具及审批
  → 结果进入聊天；运行结果与触发成功分别记录
```

**未披露**：自主 check-in 的确切唤醒算法，以及内部队列、存储结构。Routine 的公开触发规则不能证明 check-in 采用相同调度方式。

对 Go Bot 的启示：安装 Google Workspace 或 X 插件只代表可以调用服务，不应自动监听全部账号活动。监听何种事件、满足什么条件才工作，需要单独建立明确职责。

## 4. OpenAI dots：持续职责、自主再次唤醒与后台研究

官方说明 dots 可以在对话之间继续职责，自行决定暂停及再次唤醒；也支持指定时间或支持的事件。它能将工作交给后台 Agent，并由主 dot 协调结果。定期工作需要保存计划；仅连接应用不会自动创建事件监控任务。[来源：Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

后台研究有单独边界：读取允许访问的信息、保存私有笔记、关联先前工作；研究本身不发送消息、不修改外部应用，也不控制浏览器或电脑。研究结果汇报给主 dot，由它提出建议或问题。后续行动再适用相应权限和审批。[来源：Proactive research](https://learn.chatgpt.com/docs/dots/tasks-and-memory#proactive-research)

```text
持续职责 / 时间 / 支持的事件
  → dot 安排推进或后台研究
  → 后台结果回到主 dot
  → 主 dot 决定如何告知、询问或继续
```

**未披露**：决定再次唤醒的模型输出契约、底层计时器、队列及私有笔记数据库。上图是官方描述的行为关系，不是其服务端源码架构。

对 Go Bot 的启示：固定周期不是唯一选择，可以在完成一次检查后安排一个具体的下次检查时间。研究阶段与对外行动应有明确边界；不能靠提示词声称已经强制实现这个边界。

## 5. 开源代码如何完成唤醒

### 5.1 Hermes Agent：空闲时进入原会话

核对版本：`f6c3eb1a79ed769d1d4a978ec454dd690166e82d`。

`HeartbeatManager` 保存每个会话的检查指令、间隔和上次触发信息。驱动在会话空闲时检查 `due_prompt()`，有到期请求才注入普通 user-role 消息。它先保存领取信息，避免重复领取；错过多个周期合并为一次，不补发积压。状态在会话存储中，重启可恢复。[源码：heartbeat.py](https://github.com/NousResearch/hermes-agent/blob/f6c3eb1a79ed769d1d4a978ec454dd690166e82d/hermes_cli/heartbeat.py)

驱动还要求用户输入队列先清空。Gateway 对无变化的 heartbeat 可以不发送聊天输出，普通用户消息不套用这种静默规则。其 heartbeat 使用原会话；cron 则适合独立工作。[官方说明](https://github.com/NousResearch/hermes-agent/blob/f6c3eb1a79ed769d1d4a978ec454dd690166e82d/website/docs/user-guide/features/heartbeat.md)

另一个有用的具体机制是 cron 的脚本前置检查：`_parse_wake_gate()` 接受脚本末行的 `{"wakeAgent": false}`，跳过本次模型运行。即“先用确定性代码判断是否变化，必要时再叫模型”。[源码：scheduler_prompt.py](https://github.com/NousResearch/hermes-agent/blob/f6c3eb1a79ed769d1d4a978ec454dd690166e82d/cron/scheduler_prompt.py)

### 5.2 OpenClaw：当前版本已将主动检查纳入普通自动化

核对版本：`2aca1a1c1595e25d3cdb0bc7ce098bdcc92efb87`。

`createDefaultProactiveJob()` 创建普通 `agentTurn` 自动化任务，默认每 30 分钟、目标为主会话、`idleOnly: true`，检查提示允许无消息结束。它由显式 setup 创建一次，启动及重载不会重新生成用户删除的任务。[源码：default-proactive-job.ts](https://github.com/openclaw/openclaw/blob/2aca1a1c1595e25d3cdb0bc7ce098bdcc92efb87/src/cron/default-proactive-job.ts)

当前官方文档已将 heartbeat 迁移为可编辑的 automation；`HEARTBEAT.md` 不再作为运行时调度输入。任务支持静默结果、活跃时间及空闲运行。不能套用早期教程，声称当前实现仍是独立 heartbeat 循环加 `HEARTBEAT.md`。[官方说明：Heartbeat migration](https://docs.openclaw.ai/gateway/heartbeat)

这些实现证明：唤醒由模型外的常驻运行服务完成；模型不需要一直生成，客户端也不需要一直打开。周期检查可以复用已有调度设施。

## 6. 几种做法的对应关系

| 问题 | 已确认的外部做法 | Go Bot 建议 |
| --- | --- | --- |
| 为什么再次运行 | Muse 的计划/相关事件；Grok routine；dots 的时间/事件/自行跟进 | 明确职责对应时间或事件；不默认扫描全部用户数据 |
| 如何持续理解目标 | 产品使用持续上下文和记忆；Hermes 可进入原会话 | 复用保存的会话、实际工作目录及现有记忆/历史检索 |
| 如何避免忙时打断 | Hermes 空闲且用户输入优先；OpenClaw `idleOnly` | 主动检查只在会话空闲时启动，不使用 steer 抢占 |
| 如何避免每次都叫模型 | Hermes 脚本 wake gate | 能确定性检查变化的插件先比较事件或游标 |
| 如何避免每次都发消息 | Muse 判断是否值得展示；Hermes/OpenClaw 支持静默 | 执行结果与用户可见消息分开决定 |
| 谁决定对外行动 | 各产品另有授权和审批 | 继续由 Go 工具系统、权限及审批模块负责 |

表中 Go Bot 一列是本项目提案，不是外部产品已公开的内部实现。

## 7. 我们当前已具备什么

以下依据当前 Go Bot 源码，不是待实现能力：

- `harness/schedule` 已保存时间规则并向目标会话投递；`internal/hostruntime/native_schedule_delivery.go` 处理会话恢复及投递执行观察。
- `NativeRuntime.DeliverSchedule()` 将到期工作持久化进入会话 inbox，再由现有 Agent Loop 领取；并非由前端发起模型调用。
- 会话保存实际工作目录，定时任务可使用已有会话或其目标创建规则，不需要重新将会话与工作目录强绑定。
- Host 已有长期记忆及会话历史 FTS 检索；记忆更新本身不会唤醒 Agent。
- Web/Mobile 已通过账号级 SSE 接收各会话消息；客户端断开不等于 Host 停止运行。
- 插件目前可提供工具、Skill、MCP、授权等能力；SDK 尚无外部事件订阅和主动唤醒契约。

仍缺少：持续职责的明确管理、服务事件到 Agent 的入口、无变化静默展示规则，以及手机在后台/被关闭时的系统推送。SSE 不能代替 APNs/FCM 等手机推送。

现有 `goal` 用来推进当前执行目标，不应直接当作无限期监控职责。现有 schedule 负责用户保存的定时工作，也不应被偷偷改成全用户的周期扫描。

## 8. Go Bot 建议架构

### 8.1 保持当前职责边界

```text
已有时间任务 ───────────┐
插件提供的已订阅事件 ──┼→ Go 主动服务入口 → 会话 inbox → Go Agent Loop
明确保存的后续检查 ────┘                         │
                                                ├→ 工具 / Skill / MCP
                                                ├→ 原有权限及审批
                                                └→ 结果判断 → 可见消息 / 静默
                                                              │
                                                     Controller → 客户端
```

Go 管调度接入、会话、执行及结果提交。Cordis 继续管理业务插件生命周期；插件决定如何连接第三方服务和解释服务事件，不接管核心 Agent Loop。不新增 Controller 五分钟轮询，不恢复之前删除的闲置回收机制，也不另建 Redis 定时任务系统。

### 8.2 从明确委托的持续职责开始

例如：“未来一周关注这个项目的 CI，失败时说明原因，成功且没有变化就不要打扰。”

保存时明确工作范围、通知条件、目标会话及何时停止。能够用现有 schedule 表达的时间检查，直接复用原任务；不要另写一套 cron 引擎。检查完成后需要晚些时候继续的，可保存下一次一次性检查，到期仍经相同入口执行。模型建议时间，Go 验证并保存。

先支持这种明确职责，再考虑没有具体委托的自主研究。后者需要额外的数据访问及行动边界，不能因默认 `danger-full-access` 就自动扫描邮件并对外行动。

### 8.3 事件由插件采集，Host 接受后进入普通执行

以 Google Workspace 为例：Google 插件负责选择 Gmail 的事件/增量接口、刷新原生凭证、读取游标和整理必要输入；Host 负责把已订阅职责的事件送进目标会话。X 插件同理，但必须按官方实际支持的能力实现，不能假定 MCP 自动提供订阅。

建议增加一个窄的异步 SDK 入口，例如 `ctx.host.wake.enqueue({ responsibilityId, eventKey, summary })`，供插件报告已匹配事件。**这只是待设计接口，当前不存在。** Host 从保存的职责解析会话及工作目录，不允许事件随意指定别人的会话、覆盖权限或注入 system prompt。

仅当服务需要时才提供 webhook；本地私网部署可由插件主动拉取。无需为了主动服务要求所有部署者先开公网回调。

### 8.4 公共准入与运行规则

1. 检查职责仍启用、目标会话有效、必要模型及插件已配置。
2. 根据服务事件 ID/游标排除已接受的重复事件；一个检查尚未开始时，可合并同一职责的多次变化。
3. 会话有 turn 或用户输入时等待，不抢占，不产生多个积压的周期检查。
4. 到执行时读取最新的职责、会话事实、记忆及工具结果，避免保存一套长期不变的上下文快照。
5. 使用正常 Go 工具执行流程，插件工具只在其业务入口经 RPC 调用。
6. 结果是“无变化”“有进展”“需要输入”还是失败，分别处理；失败不能记为无变化。

这些是主动工作的准入规则，不是给业务插件重新开放通用 guard 或 pre/execute/post 中间件。

### 8.5 静默结果与通知

“无变化”属于一次合法的检查结果，可以保留执行事实，但不追加助手气泡、不展示短暂的“生成中”，也不发送系统通知。普通用户发出的消息不适用静默规则。

实现时要由 Go 接受明确的后台结果声明，例如内部结果 `no_change`，而不是前端在任意文本中搜索 `NO_REPLY` 并删除内容。需要可见输出时，继续使用现有 assistant 内容块与 SSE 投影，不另造一套聊天消息协议。后台检查详细过程可在任务详情查看。

同一事项没有新的进展，不重复提醒。用户应能暂停职责，并分别控制主动检查及通知。检查频率、每日模型调用额度和静默时间需要有限默认值；具体默认数值在实施前确定，不从闭源产品猜测。

在线客户端继续走现有账号级 SSE。App 后台或关闭后的提醒需要单独接入系统推送；点击通知再进入对应会话。尚未实现推送前，只能承诺会话中保存结果、重新打开可见，不能承诺手机锁屏时会收到通知。

### 8.6 权限、审批与 Host 生命周期

显式交办任务沿用现有执行权限。主动研究如果要承诺只读，必须在 Go 执行器限制可用操作；仅写“不要修改”不构成限制。无法可靠分类的 shell/MCP 操作不能直接宣称只读。

普通权限审批继续走原有机制：没有交互渠道时不执行需审批的操作；已发起后断线的等待与恢复规则保持现状。不把普通审批改成 120 秒超时，也不借主动任务绕过审批。具体授权及问题仍在所属会话回答。

Host 运行时，客户端关闭不影响其本地计划。**用户主动 Stop Host 后，Host 内计划及插件监听都停止。** Controller 不偷偷重启它。若未来要支持停止 Host 仍接收外部事件并唤醒，需要另行设计 Controller 事件入口及明确的自动启动授权，不能算当前已有能力。

### 8.7 数据保持最少

复用现有位置：

- 时间规则：`/root/harness/.dsh/storages/schedule.json`。
- 工作过程与可见回复：原会话日志及实际工作目录。
- 长期偏好与事实：现有 `.dsh/memories`；不把定时状态塞进记忆文本。
- 第三方账号令牌：插件对应的现有凭证/原生 CLI 存储；不复制进 Redis 或职责记录。

只有事件订阅、持续职责或通知去重无法由现有事实表达时，才增加一份 Host 内职责状态。其最少字段是职责 ID、指令、目标会话、启停状态、关联 schedule ID/事件来源、事件游标及上次提醒标识；时间使用 Unix 毫秒。确切存储文件与 SDK 契约留到实施设计收口，不先增加快照文件、第二份会话历史或复杂的运行状态机。

## 9. 建议实施顺序与验收

1. **明确职责 + 时间检查 + 静默结果**：复用现有 schedule/会话，验证忙时等待、无变化无气泡、有结果正常交付、暂停后不再触发。
2. **一个真实外部事件来源**：由 Google Workspace 插件实现一个范围明确的监听；验证重复事件不重复工作、未订阅不会运行、凭证过期能说明原因。
3. **Web/Mobile 提醒**：在线 SSE、未读入口、跳转原会话；再完成真实设备的系统推送及权限流程。
4. **有限的自主跟进**：在已有职责内让 Agent 选择下一次检查时间；验证完成/取消后不再安排，Host 重启后按保存事实恢复，不补发大量旧检查。

先完成一条真实的“事件变化 → Agent 判断 → 必要时提醒 → 用户继续处理”闭环，再扩展服务种类。整个过程中保持现有 schedule 上游语义，不将研究提案当作已经实现的功能。
